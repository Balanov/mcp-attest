Where it saves your day.

The review that never happens

Every change to an MCP server changes what that server may do. Run it against your policy before it merges, and let the build fail when the answer differs.

The server you inherited

You did not write the server and nobody wrote the policy. attest init reads the live tool list and scaffolds a default-deny policy you can then argue with.

The vendor's server

Point the harness at somebody else's MCP server and at the policy you require. It reports where that server deviates, with the evidence you need to send along.

The incident review

You already export OpenTelemetry. attest check --otlp replays that export against the policy and shows which calls would not have been allowed.

What the public servers look like.

The same tool that checks your server can measure the ones the official MCP registry lists. It sends the handshake and the tool list — and never calls a tool.

45.8% of the servers that answered the handshake opened a session with no credentials at all 81 of 177 · 2026-11-14
189 servers measured, every ninth of the 1,698 the registry lists 3 well-formed requests each · no tool call ever
399 sensitive tools out of the 1,049 those servers publish shell · filesystem · network · database
See the method and the caveats

The scan walks every page of the registry, keeps the servers that publish a Streamable HTTP endpoint, and takes every ninth of them — a systematic sample, the same one tomorrow. Each server gets at most three well-formed requests: initialize, the initialized notification, and tools/list. No tool is ever called, so nothing can be changed on a server that is not ours. A tool counts as sensitive when its name or its schema reaches a shell, a file, a network endpoint or a database.

This is our own measurement of public servers, not a disclosure. We publish the method and the aggregates; the host names stay with whoever runs the scan, because naming a server that accepts an unauthenticated session is a disclosure in itself.

Questions, answered plainly.

Will it call tools on a server that is not mine?

The posture scanner stops at the tool list and never calls a tool. The conformance harness calls tools only on the server you point it at, and only the ones your policy names.

Does it work with RS256 or EdDSA tokens?

The claim-level probes mint correctly signed tokens with HS256, because that is the only scheme the standard library can sign and verify without a dependency. Name a signing key through oauth.signing_key_env, or mint the token outside and point the probe at it. Without a key those probes are reported as skipped — never as passed.

What if my policy is wrong?

Then the harness tells you that. It compares a live server against the policy you wrote; it cannot know the policy you meant. The finding points at the difference and shows both sides.

What happens when a check cannot be run?

It is reported as skipped, with the reason. A check that did not run is never counted as passed — silence is not a result.

Do I need an API key, a model or a network?

No. Zero runtime dependencies, no model, no telemetry, nothing leaves your machine. The only network it touches is your server.

Which MCP servers does it work with?

Any server that speaks MCP over stdio or Streamable HTTP. The client speaks JSON-RPC directly, with no SDK, so there is no library version to match.

Where this fits among the others.

MCP testing is crowded — mcp-assert, mcp-fence, mcp-fuzz, MCP-Scan, promptfoo, mcpsnoop, mcp-conformance. Most of them fuzz a server or check a prompt. What the OWASP guide puts first is the authorization matrix and token validation, and that is what this does: every tool, every role, every identity, against a policy, on a live server.

It is not the best tool for every job. If you want to fuzz a transport, use a fuzzer. If you want to check one prompt, use a prompt tool. If you want to know whether your server refuses what your policy says it must refuse, and to hand an auditor the proof, use this one.
